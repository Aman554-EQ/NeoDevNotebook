## How this project works

Build it milestone by milestone; each solution is the real code, and each checkpoint runs its real
tests. Keep this project as a template: most new Django projects start with exactly this.

```bash
python -m pip install "Django>=5.2,<5.3" djangorestframework djangorestframework-simplejwt drf-spectacular pytest pytest-django
django-admin startproject config . && python manage.py startapp accounts
```

## The brief (PRD)

**Problem.** Every product needs accounts, and getting them wrong (plain-text passwords, guessable
reset links, endless tokens) is a security incident waiting to happen.

**Users.** Website visitors (sessions) and mobile/API clients (tokens).

**User stories.**

- A visitor can sign up with email and password and is logged in immediately.
- A user can log in and out, see a profile page, and reset a forgotten password by email.
- An API client can register, exchange email + password for tokens, refresh them, log out, and read
  or update its profile.

**Acceptance criteria.**

- Users sign in with **email**; there's no username.
- Passwords are validated (length, common passwords, similarity) and stored hashed.
- Wrong credentials give one generic message; unknown emails get the same password-reset response as
  known ones (no account enumeration).
- Access tokens expire in minutes; refresh tokens rotate and old ones are blacklisted; logout
  blacklists the refresh token.
- Registration is throttled (5 per hour per IP).
- With `DEBUG=false`, HTTPS redirect, HSTS and secure cookies are on, and `check --deploy` passes.

## Design

| Model                                            | Notes                                                                                         |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `accounts.User(AbstractUser)`                    | `username = None`, `email` unique, `USERNAME_FIELD = "email"`, `display_name`, custom manager |
| simplejwt `OutstandingToken`, `BlacklistedToken` | from `rest_framework_simplejwt.token_blacklist`                                               |

| URL                                                    | Purpose                            |
| ------------------------------------------------------ | ---------------------------------- |
| `/signup/`, `/login/`, `/logout/` (POST), `/profile/`  | website, sessions                  |
| `/password-reset/` → email → `/reset/<uid>/<token>/`   | Django's reset views               |
| `POST /api/auth/register/`                             | create an account (throttled)      |
| `POST /api/auth/token/`, `/token/refresh/`, `/logout/` | JWT pair, rotation, blacklist      |
| `GET/PATCH /api/me/`                                   | the current user (email read-only) |

## Harden

- The signing key for JWTs (`JWT_SIGNING_KEY`) is separate from `SECRET_KEY`, so all API tokens can be
  revoked without logging out website sessions.
- `.env.example` documents every variable with **fake** values; tests always load it, so they never
  need real secrets.
- When `DEBUG` is off: `SECURE_SSL_REDIRECT`, `SECURE_HSTS_*`, `SESSION_COOKIE_SECURE`,
  `CSRF_COOKIE_SECURE`; a test reloads the settings with production values to prove it.
