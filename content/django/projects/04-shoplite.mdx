## The brief (PRD)

**Problem.** A small shop sells books and games online. It needs a website for browsing and checkout,
and an API for a mobile app, without ever selling stock it doesn't have or charging twice.

**Users.** Guests (browse, fill a cart), customers (check out, see their orders, cancel pending ones),
staff (manage the catalogue, see all orders, ship), and the payment provider (confirms payments).

**User stories.**

- Guests browse products by category and add them to a cart that survives page loads.
- Customers check out on the website or through the API, and pay through the payment provider.
- Customers see only their own orders; they can cancel an order that hasn't been paid.
- Staff manage products and categories and ship paid orders.
- The payment provider notifies the shop when a payment succeeds or fails.

**Acceptance criteria.**

- Stock can't go negative, even with many simultaneous checkouts.
- A retried checkout with the same `Idempotency-Key` returns the first result and creates nothing new;
  the same key with a different body is a 422.
- Webhooks are accepted only with a valid HMAC signature and a fresh timestamp; duplicates are
  acknowledged and ignored; a wrong amount doesn't mark an order paid.
- Every API error has the shape `{"error": {"code", "message", "details", "request_id"}}`.
- Every response carries `X-Request-ID`; logs include it.
- Order lists cost a fixed number of queries; categories are cached and invalidated on change.
- `/health/` never touches the database; `/ready/` reports database and cache and answers 503 when
  either fails.
- Production settings pass `check --deploy` with zero warnings.

**Non-goals.** Real card processing, shipping rates, multi-currency, a front-end framework.

## Design

**Data model.**

| Model                   | Key fields                                                                    | Rules                                                        |
| ----------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `accounts.User`         | `email` (login), `is_staff` (staff role)                                      | custom user from day one                                     |
| `catalog.Category`      | `name`, `slug`                                                                | unique                                                       |
| `catalog.Product`       | `category` (PROTECT), `name`, `slug`, `price` (Decimal), `stock`, `is_active` | `price >= 0` check; index (category, is_active)              |
| `orders.Order`          | `user` (PROTECT), `status`, `total`                                           | state machine: pending → paid → shipped, pending → cancelled |
| `orders.OrderItem`      | `order` (CASCADE), `product` (PROTECT), `quantity`, `unit_price`              | one line per product; quantity ≥ 1; price copied at purchase |
| `orders.IdempotencyKey` | `user`, `key`, `fingerprint`, `response_status`, `response_body`              | unique (user, key)                                           |
| `payments.Payment`      | `order`, `provider_ref` (unique), `amount`, `status`                          |                                                              |
| `payments.WebhookEvent` | `event_id` (unique), `type`                                                   | makes duplicate deliveries no-ops                            |

**API (v1).** See the README table below; the full contract is the generated OpenAPI schema.

**Architecture.** Apps by domain (`accounts`, `catalog`, `cart`, `orders`, `payments`, `core`); every
business rule in `orders/services.py`; views (web and API) only translate HTTP; one module talks to the
payment provider.

## Harden

- **Money:** `DecimalField` everywhere; prices copied into order lines; webhook amounts compared with the
  stored payment.
- **Concurrency:** row locks in a consistent order, `F()` updates, unique constraints for idempotency keys
  and webhook events, a CHECK constraint on price and quantity.
- **Access:** customers only see their own orders (scoped querysets, object permission, 404 on the web);
  staff-only shipping and catalogue edits.
- **Abuse:** throttled order creation; capped page sizes; sanitised request ids.
- **Secrets:** every secret from the environment; `.env.example` has fakes; tests never need real ones.
- **Transport:** HTTPS redirect, HSTS, secure cookies, CSP for HTML, CORS limited to `/api/` and listed
  origins.
