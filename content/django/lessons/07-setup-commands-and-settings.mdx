## Intuition: one control panel for the whole project

`manage.py` is your project's control panel. Every task, from running the dev server to changing the
database schema, inspecting data, running tests or preparing a deployment, is a command on it. It
works because it first loads **your settings**, so every command knows your apps, your database and
your configuration.

## The precise rules

**Creating a project:**

```bash
mkdir notes && cd notes
python -m venv .venv
# Windows: .venv\Scripts\activate     macOS/Linux: source .venv/bin/activate
python -m pip install "Django>=5.2,<5.3"
django-admin startproject config .     # the dot: create it here, not in a nested folder
python manage.py startapp notes        # then add "notes" to INSTALLED_APPS
python manage.py migrate               # create Django's own tables
python manage.py runserver             # http://127.0.0.1:8000/
```

Here is the real layout of this module's **Notes** project, generated from its files:

<ProjectTree project="notes" />

| File                                                             | Job                                                                   |
| ---------------------------------------------------------------- | --------------------------------------------------------------------- |
| `manage.py`                                                      | runs commands with `DJANGO_SETTINGS_MODULE` pointing at your settings |
| `config/settings.py`                                             | all configuration                                                     |
| `config/urls.py`                                                 | the root URLconf                                                      |
| `config/wsgi.py`, `asgi.py`                                      | entry points for production servers (gunicorn, uvicorn)               |
| `notes/models.py`, `views.py`, `urls.py`, `forms.py`, `admin.py` | the app's code                                                        |
| `notes/migrations/`                                              | schema history, committed to Git                                      |
| `notes/templates/notes/`                                         | templates, namespaced by the app name                                 |

**The commands you'll use most:**

| Command                                                        | Does                                                         |
| -------------------------------------------------------------- | ------------------------------------------------------------ |
| `runserver`                                                    | development server with auto-reload (never in production)    |
| `makemigrations` / `migrate` / `showmigrations` / `sqlmigrate` | schema changes (lesson 10)                                   |
| `createsuperuser`                                              | an admin user                                                |
| `shell` / `dbshell`                                            | Python or the database's own client, with the project loaded |
| `check` / `check --deploy`                                     | configuration problems / production security problems        |
| `test`                                                         | the test suite against a fresh test database                 |
| `dumpdata` / `loaddata`                                        | export and import data as JSON fixtures                      |
| `collectstatic`                                                | copy static files into `STATIC_ROOT` for the web server      |
| `diffsettings`                                                 | which settings differ from Django's defaults                 |

**The settings that matter** (this is the Notes project's real `settings.py`):

<ProjectFile project="notes" path="config/settings.py" />

- `SECRET_KEY` signs sessions, password-reset links and CSRF tokens. It comes from the environment;
  a leaked key lets attackers forge them.
- `DEBUG=True` shows detailed error pages with your settings and code. **Never in production.**
- `ALLOWED_HOSTS` lists the domain names this site answers to (protects against Host-header attacks).
- `INSTALLED_APPS` and `MIDDLEWARE`: what Django loads, and the order requests pass through.
- `DATABASES`, `TEMPLATES`, `AUTH_PASSWORD_VALIDATORS`, time zone (`USE_TZ=True` stores UTC), static
  files and `DEFAULT_AUTO_FIELD` (64-bit primary keys).

**The playground.** The lessons run Django from a single file with
[playground.py](/downloads/django/playground.py). It does in memory what `settings.py`,
`urls.py` and `manage.py migrate` do in a project:

```python norun title="playground.py"
"""playground.py: run Django from a single file while you learn.

A real project spreads its setup over settings.py, urls.py and manage.py. To try one idea at a
time, it is handier to keep everything in one script. Save this file next to your examples and
start each example with:

    from playground import setup
    setup()

Models, views and `urlpatterns` you define in that script then work as if they lived in an app
called "shop". Requires: python -m pip install "Django>=5.2,<5.3"
"""

import sys
import traceback
import unittest

import django
from django.apps import AppConfig
from django.conf import settings


class PlaygroundApp(AppConfig):
    """Makes the script you run (the __main__ module) a Django app labelled "shop"."""

    name = "__main__"
    label = "shop"
    default_auto_field = "django.db.models.BigAutoField"

    def import_models(self):
        # A script has no models.py: its own classes are the models (so `migrate` creates them).
        self.models = self.apps.all_models[self.label]
        self.models_module = self.module


def setup(*, apps=(), templates=None, middleware=None, script_tags=False, **overrides):
    """Configure Django in memory: an SQLite database, the script's urlpatterns, optional templates.

    apps:       extra INSTALLED_APPS, e.g. ["rest_framework"]
    templates:  {"name.html": "template source"} served by an in-memory template loader
    script_tags: True if the script defines custom template filters/tags
                (register = template.Library()); they become available in every template
    middleware: replaces the default MIDDLEWARE list
    overrides:  any other setting, e.g. DEBUG=False or REST_FRAMEWORK={...}
    """
    config = dict(
        DEBUG=True,
        # A fake key for learning only. Real projects read SECRET_KEY from the environment.
        SECRET_KEY="playground-not-a-real-secret",
        ALLOWED_HOSTS=["testserver", "localhost", "127.0.0.1"],
        ROOT_URLCONF="__main__",
        INSTALLED_APPS=[
            "django.contrib.contenttypes",
            "django.contrib.auth",
            "django.contrib.sessions",
            "django.contrib.messages",
            *apps,
            "playground.PlaygroundApp",
        ],
        MIDDLEWARE=middleware
        if middleware is not None
        else [
            "django.middleware.security.SecurityMiddleware",
            "django.contrib.sessions.middleware.SessionMiddleware",
            "django.middleware.common.CommonMiddleware",
            "django.middleware.csrf.CsrfViewMiddleware",
            "django.contrib.auth.middleware.AuthenticationMiddleware",
            "django.contrib.messages.middleware.MessageMiddleware",
        ],
        DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}},
        TEMPLATES=[
            {
                "BACKEND": "django.template.backends.django.DjangoTemplates",
                "OPTIONS": {
                    "loaders": [
                        ("django.template.loaders.locmem.Loader", templates or {}),
                        "django.template.loaders.app_directories.Loader",  # e.g. the admin's
                    ],
                    "builtins": ["__main__"] if script_tags else [],
                    "context_processors": [
                        "django.template.context_processors.request",
                        "django.contrib.auth.context_processors.auth",
                        "django.contrib.messages.context_processors.messages",
                    ],
                },
            }
        ],
        STATIC_URL="static/",
        # Fast hashing keeps examples quick. Never use MD5 for real passwords.
        PASSWORD_HASHERS=["django.contrib.auth.hashers.MD5PasswordHasher"],
        USE_TZ=True,
        TIME_ZONE="UTC",
    )
    config.update(overrides)
    settings.configure(**config)
    django.setup()


def postgres_database():
    """A brand-new PostgreSQL database for one example, dropped again when the script ends.

    Reads the server from the DATABASE_URL environment variable, e.g.
    postgres://user:password@localhost:5432/postgres. Use it as
    setup(DATABASES={"default": postgres_database()}). Your existing databases are never touched.
    Requires: python -m pip install "psycopg[binary]"
    """
    import atexit
    import os
    import uuid
    from urllib.parse import urlsplit

    import psycopg

    url = os.environ["DATABASE_URL"]
    server = urlsplit(url)
    name = f"playground_{uuid.uuid4().hex[:10]}"
    admin = psycopg.connect(url, autocommit=True)
    admin.execute(f'CREATE DATABASE "{name}"')

    def drop():
        from django.db import connections

        connections.close_all()
        admin.execute(f'DROP DATABASE IF EXISTS "{name}" WITH (FORCE)')
        admin.close()

    atexit.register(drop)
    return {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": name,
        "USER": server.username,
        "PASSWORD": server.password,
        "HOST": server.hostname,
        "PORT": server.port or 5432,
    }


def migrate():
    """Create the tables of Django's built-in apps and of every model defined so far."""
    from django.core.management import call_command

    call_command("migrate", run_syncdb=True, verbosity=0)


class _Result(unittest.TestResult):
    """Prints one line per test (no timings, so the output is the same on every run)."""

    def addSuccess(self, test):
        super().addSuccess(test)
        print(f"  ok    {test._testMethodName}")

    def _bad(self, test, err, word):
        last = traceback.format_exception_only(err[0], err[1])[-1].strip()
        print(f"  {word}  {test._testMethodName}: {last}")

    def addFailure(self, test, err):
        super().addFailure(test, err)
        self._bad(test, err, "FAIL")

    def addError(self, test, err):
        super().addError(test, err)
        self._bad(test, err, "ERROR")


def run_tests(*cases):
    """Run Django TestCase classes against a fresh test database, like `manage.py test`."""
    from django.test.runner import DiscoverRunner
    from django.test.utils import setup_test_environment, teardown_test_environment

    from django.db import connection

    # Django never closes an in-memory SQLite connection. Drop it so the tests get their own
    # empty database (like `manage.py test`) instead of rows the script created earlier.
    if connection.connection is not None:
        connection.connection.close()
        connection.connection = None
    runner = DiscoverRunner(verbosity=0, interactive=False)
    setup_test_environment()
    old_config = runner.setup_databases()
    try:
        loader = unittest.defaultTestLoader
        suite = unittest.TestSuite(loader.loadTestsFromTestCase(case) for case in cases)
        result = _Result()
        suite.run(result)
    finally:
        runner.teardown_databases(old_config)
        teardown_test_environment()
    failed = len(result.failures) + len(result.errors)
    passed = result.testsRun - failed
    print(f"{passed} passed" + (f", {failed} failed" if failed else ""))
    return result.wasSuccessful()


if __name__ == "__main__":
    sys.exit("Import this file from your examples: from playground import setup")
```

- `setup()` calls `settings.configure(...)` instead of reading a settings module, with
  `ROOT_URLCONF="__main__"` so the `urlpatterns` in your script are the URLconf.
- `PlaygroundApp` turns your script into an app labelled `shop`, so models you define there get
  tables named `shop_<model>`.
- `migrate()` runs the real `migrate` command with `run_syncdb=True`: tables for apps without
  migration files are created directly. Real apps always use migrations (lesson 10).
- `run_tests()` runs Django `TestCase` classes against a fresh test database, like
  `manage.py test`, and prints one line per test.
- It uses the MD5 password hasher purely for speed. Real projects keep Django's slow default.

## Worked example

Django's **system check framework** inspects your configuration. `manage.py check` runs it, and
`check --deploy` adds production security checks. Here it is from code, against a configuration that
isn't production-ready yet.

```python title="checks.py"
from playground import setup

setup(DEBUG=False)

from django.core import checks

urlpatterns = []  # checks also validate the URLconf, so it must exist

issues = checks.run_checks(include_deployment_checks=True)
for issue in sorted(issues, key=lambda i: i.id):
    print(issue.id, "-", issue.msg.split(". ")[0])  # the first sentence of each message
print(len(issues), "issues")
```

```text title="Output"
security.W002 - You do not have 'django.middleware.clickjacking.XFrameOptionsMiddleware' in your MIDDLEWARE, so your pages will not be served with an 'x-frame-options' header
security.W004 - You have not set a value for the SECURE_HSTS_SECONDS setting
security.W008 - Your SECURE_SSL_REDIRECT setting is not set to True
security.W009 - Your SECRET_KEY has less than 50 characters, less than 5 unique characters, or it's prefixed with 'django-insecure-' indicating that it was generated automatically by Django
security.W012 - SESSION_COOKIE_SECURE is not set to True
security.W016 - You have 'django.middleware.csrf.CsrfViewMiddleware' in your MIDDLEWARE, but you have not set CSRF_COOKIE_SECURE to True
6 issues
```

Each warning maps to a setting: `W004` asks for `SECURE_HSTS_SECONDS`, `W008` for
`SECURE_SSL_REDIRECT`, `W009` for a long random `SECRET_KEY`, `W012` and `W016` for secure cookies,
and `W002` for the clickjacking middleware the playground leaves out. The **Auth starter** project
turns all of them on when `DEBUG` is off, and its tests run `check --deploy` to prove it.

## Variations

### A custom management command

```python
from io import StringIO

from playground import migrate, setup

setup()

from django.contrib.auth.models import User
from django.core.management import call_command
from django.core.management.base import BaseCommand, CommandError


class Command(BaseCommand):  # in a project: <app>/management/commands/seed_users.py
    help = "Create demo users."

    def add_arguments(self, parser):
        parser.add_argument("count", type=int)
        parser.add_argument("--prefix", default="user")

    def handle(self, count, prefix, **options):
        if count > 100:
            raise CommandError("Let's not create more than 100 demo users.")
        for n in range(1, count + 1):
            User.objects.get_or_create(username=f"{prefix}{n}")
        self.stdout.write(self.style.SUCCESS(f"{User.objects.count()} users in total"))


migrate()
out = StringIO()
call_command(Command(), "3", "--prefix", "demo", stdout=out)
print(out.getvalue().strip())
print(list(User.objects.values_list("username", flat=True)))
try:
    call_command(Command(), "500")
except CommandError as exc:
    print("CommandError:", exc)
```

```text title="Output"
3 users in total
['demo1', 'demo2', 'demo3']
CommandError: Let's not create more than 100 demo users.
```

In a project the class must be named `Command` in `<app>/management/commands/<name>.py`; then
`python manage.py seed_users 3 --prefix demo` runs it. `call_command` runs any command from code,
which is how tests exercise them. ShopLite's `simulate_payment` command is a real example.

### Fixtures: dumpdata and loaddata

```python
import tempfile
from io import StringIO
from pathlib import Path

from playground import migrate, setup

setup()

from django.core.management import call_command
from django.db import models


class Category(models.Model):
    name = models.CharField(max_length=50)


migrate()
Category.objects.create(name="Books")
Category.objects.create(name="Games")

out = StringIO()
call_command("dumpdata", "shop.category", indent=1, stdout=out)
print(out.getvalue().strip())

with tempfile.TemporaryDirectory() as folder:
    fixture = Path(folder) / "categories.json"
    fixture.write_text(out.getvalue())
    Category.objects.all().delete()
    call_command("loaddata", str(fixture), verbosity=0)
print(list(Category.objects.order_by("pk").values_list("pk", "name")))
```

```text title="Output"
[
{
 "model": "shop.category",
 "pk": 1,
 "fields": {
  "name": "Books"
 }
},
{
 "model": "shop.category",
 "pk": 2,
 "fields": {
  "name": "Games"
 }
}
]
[(1, 'Books'), (2, 'Games')]
```

Fixtures are JSON (or YAML) snapshots of rows, primary keys included. They're handy for demo data
and reference data; for test data, factories (lesson 26) are easier to maintain.

### Creating a superuser without prompts

```python
import os

from playground import migrate, setup

setup()

from django.contrib.auth.models import User
from django.core.management import call_command

migrate()
os.environ["DJANGO_SUPERUSER_PASSWORD"] = "fake-admin-pass-for-learning"  # e.g. from CI secrets
call_command("createsuperuser", interactive=False, username="admin", email="admin@example.com",
             verbosity=0)
admin = User.objects.get(username="admin")
print(admin.is_superuser, admin.is_staff, admin.check_password("fake-admin-pass-for-learning"))
```

```text title="Output"
True True True
```

`--noinput` plus `DJANGO_SUPERUSER_PASSWORD` is how deployment scripts and containers create the
first admin without a human at the keyboard.

### Temporarily different settings

```python
from playground import setup

setup()

from django.conf import settings
from django.test import override_settings

print("before:", settings.DEBUG, settings.LANGUAGE_CODE)
with override_settings(DEBUG=False, LANGUAGE_CODE="de"):
    print("inside:", settings.DEBUG, settings.LANGUAGE_CODE)
print("after: ", settings.DEBUG, settings.LANGUAGE_CODE)
```

```text title="Output"
before: True en-us
inside: False de
after:  True en-us
```

Settings are read-only at runtime; `override_settings` (also a decorator for test methods and
classes) changes them only inside a block, which is how tests check production-only behaviour. With
pytest-django you use the `settings` fixture instead.

### Reading a .env-style environment into settings

```python
import os

os.environ.update({  # what a .env file or the hosting platform would provide
    "DJANGO_DEBUG": "false",
    "DJANGO_SECRET_KEY": "fake-prod-key-0123456789abcdefghijklmnopqrstuvwxyzABCDEFGH",
    "DJANGO_ALLOWED_HOSTS": "shop.example.com,www.shop.example.com",
})

from playground import setup

setup(
    DEBUG=os.environ.get("DJANGO_DEBUG", "false").lower() == "true",
    SECRET_KEY=os.environ["DJANGO_SECRET_KEY"],
    ALLOWED_HOSTS=os.environ["DJANGO_ALLOWED_HOSTS"].split(","),
)

from django.conf import settings
from django.test import Client
from django.http import HttpResponse
from django.urls import path

urlpatterns = [path("", lambda request: HttpResponse("ok"))]
client = Client()
print(settings.DEBUG, settings.ALLOWED_HOSTS)
print(client.get("/", HTTP_HOST="shop.example.com").status_code)
print(client.get("/", HTTP_HOST="evil.example").status_code, "(host not allowed)")
```

```text title="Output"
False ['shop.example.com', 'www.shop.example.com']
200
400 (host not allowed)
```

With `DEBUG=False`, a request for a host that isn't in `ALLOWED_HOSTS` is refused with `400 Bad
Request`. Forgetting to add your real domain is the classic "works locally, 400 in production" bug.

## Putting it together

A typical first-deploy checklist, scripted: create the schema, seed reference data with a custom
command, create the admin from environment variables, export a fixture, and run the deployment
checks with production-like settings.

```python title="bootstrap.py"
import os
from io import StringIO

os.environ["DJANGO_SUPERUSER_PASSWORD"] = "fake-admin-pass-for-learning"

from playground import migrate, setup

setup(
    DEBUG=False,
    SECRET_KEY="fake-prod-key-0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKL",
    SECURE_HSTS_SECONDS=31536000,
    SECURE_HSTS_INCLUDE_SUBDOMAINS=True,
    SECURE_HSTS_PRELOAD=True,
    SECURE_SSL_REDIRECT=True,
    SESSION_COOKIE_SECURE=True,
    CSRF_COOKIE_SECURE=True,
    middleware=[
        "django.middleware.security.SecurityMiddleware",
        "django.contrib.sessions.middleware.SessionMiddleware",
        "django.middleware.common.CommonMiddleware",
        "django.middleware.csrf.CsrfViewMiddleware",
        "django.contrib.auth.middleware.AuthenticationMiddleware",
        "django.contrib.messages.middleware.MessageMiddleware",
        "django.middleware.clickjacking.XFrameOptionsMiddleware",
    ],
)

from django.core import checks
from django.core.management import call_command
from django.core.management.base import BaseCommand
from django.db import models

urlpatterns = []


class Currency(models.Model):
    code = models.CharField(max_length=3, unique=True)


class SeedCurrencies(BaseCommand):
    def handle(self, **options):
        created = [c for c in ("EUR", "USD", "GBP") if Currency.objects.get_or_create(code=c)[1]]
        self.stdout.write(f"created {len(created)} currencies")


steps = []
migrate()
steps.append("migrate: done")
out = StringIO()
call_command(SeedCurrencies(), stdout=out)
call_command(SeedCurrencies(), stdout=out)  # safe to run twice: get_or_create
steps.append("seed: " + " / ".join(out.getvalue().split("\n")[:2]))
call_command("createsuperuser", interactive=False, username="admin", email="a@example.com", verbosity=0)
steps.append("superuser: created")
dump = StringIO()
call_command("dumpdata", "shop.currency", stdout=dump)
steps.append(f"fixture: {dump.getvalue().count('code')} currencies exported")
issues = checks.run_checks(include_deployment_checks=True)
steps.append(f"check --deploy: {len(issues)} issues {[i.id for i in issues]}")
print("\n".join(steps))
```

```text title="Output"
migrate: done
seed: created 3 currencies / created 0 currencies
superuser: created
fixture: 3 currencies exported
check --deploy: 0 issues []
```

Every deployment warning from the worked example is gone, because each security setting is now set
and the clickjacking middleware is back. Running the seed command twice created nothing new the
second time: deployment steps should always be safe to repeat (idempotent).

## Common mistakes

<Callout type="warning" title="DEBUG = True in production">
  Debug pages show your settings, environment variables, SQL and source code to anyone who triggers
  an error. Read `DEBUG` from the environment with a default of `False`, and let `check --deploy`
  catch it.
</Callout>

- **A hard-coded `SECRET_KEY` in Git.** Read it from the environment; `startproject`'s generated key
  starts with `django-insecure-` for a reason.
- **Forgetting `ALLOWED_HOSTS`** in production: every request gets `400 Bad Request`.
- **Running Python files directly** (`python notes/views.py`) instead of through `manage.py` or
  `manage.py shell`: settings aren't loaded and imports fail.
- **Editing the database by hand instead of using migrations**: your schema and migration history
  drift apart.
- **Using `runserver` to serve real traffic.** It's single-purpose and not hardened.

  (from an environment variable).
</Reveal>

<KeyTakeaways>

- `startproject` creates the configuration package; `startapp` creates one domain area; register
  apps in `INSTALLED_APPS`.
- `manage.py` loads your settings and runs every task: runserver, migrations, shell, check, test,
  collectstatic, your own commands.
- Settings come from the environment: secret key, debug, hosts, database. Safe defaults; never
  `DEBUG=True` in production.
- `check --deploy` lists the production security settings you still need.
- The playground is a project squeezed into one file for learning; real projects split it into
  settings, URLs, apps and migrations.

</KeyTakeaways>
